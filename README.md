## 2. 技术栈介绍

### 2.1 技术总览

```
输入视频
   │
   ▼
┌──────────────────────────────┐
│  YOLOv8n (目标检测)           │  ← 找出每帧画面中所有车辆的位置
│  运行设备: CPU (OpenVINO 加速) │
└──────────────┬───────────────┘
               │  检测框列表 (每辆车的位置坐标)
               ▼
┌──────────────────────────────┐
│  ByteTrack (多目标跟踪)       │  ← 给每辆车分配唯一 ID，跨帧追踪
│  算法: 卡尔曼滤波 + 匈牙利匹配 │
└──────────────┬───────────────┘
               │  带 ID 的跟踪框列表
               ▼
┌──────────────────────────────┐
│  HSV 颜色分类                 │  ← 裁剪车身区域 → 判断颜色
│  色彩空间: HSV (色调/饱和度/亮度) │
└──────────────┬───────────────┘
               │  每辆车的颜色 + 类型
               ▼
         统计结果输出
```

### 2.2 什么是 YOLO？

**YOLO**（You Only Look Once，你只看一次）是目前工业界最主流的目标检测算法。

**核心思想**：传统的检测方法需要用"滑动窗口"反复扫描图像（慢），YOLO 则把整张图一次性送入神经网络，直接输出所有目标的位置和类别（快）。

打个比方：
- **传统方法** = 用放大镜逐行逐列扫描一张地图找房子
- **YOLO** = 看一眼地图，一次性标出所有房子的位置

**YOLOv8n** 中的 "n" 代表 **nano（纳米）**，是最小、最快的版本。系列从小到大依次是：n（nano）→ s（small）→ m（medium）→ l（large）→ x（xlarge）。nano 版精度稍低但速度最快，适合我们的场景。

**COCO 数据集**：YOLOv8 在 COCO 数据集上预训练。COCO 包含 80 个常见类别，其中和车辆相关的有：

| 类 ID | 类别 | 我们映射为 |
|-------|------|-----------|
| 2 | car | 小汽车 |
| 3 | motorcycle | 其他 |
| 5 | bus | 公交车 |
| 7 | truck | 卡车 |

### 2.3 什么是 ByteTrack？

**ByteTrack** 是目前最先进的多目标跟踪（MOT）算法之一。

**为什么需要跟踪？** 检测只能告诉你"这一帧画面中有几辆车"，但跟踪才能告诉你"这辆车在上一帧是同一辆车"。没有跟踪，同一辆车在每帧都会被当成新车，导致车流量统计严重偏高（或者严重偏低，如果只用计数线的话）。

**ByteTrack 的核心创新 — 双阈值机制（BYTE）**：

大多数跟踪器只使用高置信度的检测结果，把低置信度的直接丢弃。ByteTrack 的关键创新是：**低分检测结果也保留，在第二步单独处理**。

```
检测结果
   │
   ├── 高分检测 (置信度 > 0.5) → 优先和现有轨迹匹配
   │                               ├── 匹配成功 → 更新轨迹
   │                               └── 匹配失败 → 创建新轨迹
   │
   └── 低分检测 (0.1 < 置信度 < 0.5) → 和"上一步未匹配的高分轨迹"再匹配
                                         ├── 匹配成功 → 更新轨迹（拯救了被遮挡的车）
                                         └── 匹配失败 → 丢弃（可能是误检）
```

**为什么这样设计？** 当车辆被遮挡时，置信度会骤降。传统方法会直接丢掉这些低分检测，导致轨迹断裂。ByteTrack 用低分检测去"救"那些暂时丢失的轨迹，大大减少了 ID 切换。

**算法中的三个主要组件**：

| 组件 | 作用 | 简单理解 |
|------|------|---------|
| 卡尔曼滤波 (Kalman Filter) | 预测车辆下一帧的位置 | 根据历史运动轨迹，"猜"车辆会出现在哪 |
| 匈牙利算法 (Hungarian Algorithm) | 最优匹配（哪检测属于哪轨迹） | 解决"指派问题"：N 个检测怎么分配给 M 条轨迹，总代价最小 |
| IoU (交并比) | 衡量两个框的重叠程度 | 两个框重叠越多，越可能是同一辆车 |

**卡尔曼滤波详解**：

卡尔曼滤波器分两步工作：
1. **预测**：根据车辆之前的运动状态（位置、速度），预测它在下一帧会在哪里
2. **更新**：拿到实际检测位置后，在"预测值"和"观测值"之间取最优估计

这就像你蒙着眼睛走直线 — 你的大脑（卡尔曼滤波）会根据之前的步幅预测你下一步的位置，但如果你碰到了障碍物（检测结果），就会修正预测。

**匈牙利算法 + IoU 匹配详解**：

假设当前有 3 条轨迹（已跟踪的车辆），新来了 3 个检测框。怎么知道哪个检测对应哪条轨迹？

构建一个"代价矩阵"：

```
        检测1  检测2  检测3
轨迹A  [ 0.2    0.8    0.9 ]   ← 轨迹A 和检测1 代价最小(IoU高)
轨迹B  [ 0.9    0.3    0.8 ]
轨迹C  [ 0.8    0.9    0.1 ]   ← 轨迹C 和检测3 代价最小
```

匈牙利算法就是找到一种"一对一的全局最优配对方案"使得总代价最小。在上面的例子中，最优配对是：A→检测1，B→检测2，C→检测3。

### 2.4 什么是 OpenVINO？

**OpenVINO**（Open Visual Inference & Neural network Optimization，开放视觉推理和神经网络优化）是 Intel 推出的**模型推理加速工具套件**。

**核心作用**：把训练好的神经网络模型转换、优化，然后在 Intel 硬件（CPU、GPU、NPU）上跑得更快。

```
PyTorch 模型 (yolov8n.pt)
        │
        │  export(format="openvino")
        ▼
OpenVINO IR 模型 (yolov8n.xml + yolov8n.bin)
        │
        │  compile_model(model, "CPU")
        ▼
      推理引擎（在 CPU 上运行，速度比原始 PyTorch 快 2-3 倍）
```

**为什么用 OpenVINO 而不是直接用 PyTorch？**

| | PyTorch (CPU) | OpenVINO (CPU) |
|------|------|------|
| 推理速度 | ~15-20 fps | ~30-35 fps |
| 内存占用 | 较高 | 较低 |
| Intel 优化 | 无 | 针对 Intel CPU 深度优化 |

> **注意**：本机有 Intel Core Ultra 7 155H，内置 NPU（神经网络处理器）。理论上 OpenVINO 可以调用 NPU 进一步加速（~44 fps），但当前使用的 Ultralytics ByteTrack 管线无法直接调用 Intel NPU，因此实际工作于 CPU 模式。

### 2.5 什么是 NPU？

**NPU**（Neural Processing Unit，神经网络处理器）是专门为 AI 推理设计的硬件加速器。

| 处理器类型 | 擅长 | 类比 |
|------|------|------|
| CPU | 通用计算，串行任务 | 瑞士军刀 — 什么都能做 |
| GPU | 并行计算，图形渲染 | 1000 个小学生同时做简单加减法 |
| NPU | AI 推理（矩阵运算） | 专用计算器 — 只做乘法，但做得极快 |

Intel Core Ultra 7 155H 内置的 NPU 专门优化了神经网络中最常见的操作（卷积、矩阵乘法），功耗远低于 GPU 但速度远快于 CPU。

**本项目为什么最终没用到 NPU？**

Ultralytics 框架的 ByteTrack 在调用 OpenVINO 时，内部选择设备为 CPU，没有暴露切换 NPU 的接口。我们尝试过用底层 OpenVINO API 指定 NPU + 独立 ByteTrack 库，但效果有差距（159 vs 232 辆车）。权衡之下，选择 CPU + 完整 ByteTrack 以获得更准确的跟踪结果。

### 2.6 什么是 HSV 颜色空间？

**为什么不用 RGB？** RGB（红绿蓝）是给显示器用的，不是给人眼用的。同一个颜色在不同光照下，RGB 值差异巨大。

**HSV**（Hue 色调, Saturation 饱和度, Value 亮度）将颜色和亮度分离：

| 分量 | 含义 | 范围 |
|------|------|------|
| H（色调） | 是什么颜色（红/蓝/绿...） | 0-180（OpenCV） |
| S（饱和度） | 颜色有多"纯"（鲜艳 vs 灰白） | 0-255 |
| V（亮度） | 有多亮（黑 vs 白） | 0-255 |

**举例**：
- 白色车在阳光下 vs 阴影里 → RGB 变化很大，但 HSV 中只是 V（亮度）变了，H 和 S 基本不变
- 红色车 → H 在 0-10 或 170-180，S 很高

**本项目的颜色判定逻辑**（基于采样车辆 ROI 中心区域 60%）：

```
白色: S < 45 且 V > 150（低饱和度 + 高亮度）
黑色: V < 80（亮度很低）
红色: H ∈ [0,10] 或 [170,180]，且 S > 50
其他: 以上都不满足
```

## 6. 核心原理详解

### 6.1 完整流程图

```
视频读取 (cv2.VideoCapture)
   │
   │  逐帧读取
   ▼
┌──────────────────────────────────────────────────┐
│                  每一帧的处理                      │
│                                                    │
│  1. YOLO 检测 (model.track)                       │
│     输入: 一帧画面 (854×480 BGR)                   │
│     输出: 所有车辆的位置框 + 类别 + 置信度          │
│                                                    │
│  2. ByteTrack 跟踪 (内置于 model.track)            │
│     输入: 所有检测框                                │
│     输出: 每个框附带唯一的 track_id                 │
│                                                    │
│  3. 颜色识别 (classify_color)                      │
│     输入: 车辆 ROI（裁剪出的车辆区域）              │
│     步骤: BGR→HSV → 中心60%采样 → 阈值判断         │
│     输出: "白色"/"黑色"/"红色"/"其他"              │
│                                                    │
│  4. 颜色投票 (CollectionsCounter)                  │
│     同一 track_id，收集所有帧的颜色分类结果          │
│     取出现次数最多的颜色作为最终颜色                 │
│                                                    │
│  5. 中文标注 (draw_chinese_labels)                 │
│     OpenCV 不支持中文 → 用 Pillow 渲染中文字体      │
│                                                    │
│  6. 写入输出视频                                    │
└──────────────────────────────────────────────────┘
```

### 6.2 YOLO 检测原理

**YOLOv8 的输入和输出**：

```
输入: 图像 (640×640×3, RGB, 归一化到 0-1)
         │
         ▼
    ┌─────────┐
    │ 72 层    │  ← 卷积层 + 池化层 + 激活函数...
    │ 神经网络 │
    └────┬────┘
         │
         ▼
输出: 张量 [1, 84, 8400]
      │    │    │
      │    │    └── 8400 个候选检测位置（80×80 + 40×40 + 20×20 三个尺度的网格）
      │    └─────── 每个位置输出 84 个值：
      │               前 4 个 → 边界框坐标 (cx, cy, w, h)
      │               后 80 个 → 80 个类别的置信度
      └──────────── 批量大小（一次处理 1 张图）
```

**为什么是 8400 个候选位置？**

YOLOv8 在三个不同尺度上进行检测：

| 尺度 | 网格尺寸 | 候选数 |
|------|---------|--------|
| 大目标 | 20×20 | 400 |
| 中目标 | 40×40 | 1600 |
| 小目标 | 80×80 | 6400 |
| **合计** | | **8400** |

每个网格点预测一个边界框。大尺度（80×80）负责检测远处的小车，小尺度（20×20）负责检测近处的大车。

**边界框解码**：

YOLO 输出的不是直接的像素坐标，而是相对于网格单元的偏移：

```
cx_grid = sigmoid(cx_raw) * 2 - 0.5 + grid_x  # 中心点 x 坐标（相对于网格）
cy_grid = sigmoid(cy_raw) * 2 - 0.5 + grid_y  # 中心点 y 坐标
w = (sigmoid(w_raw) * 2)² * anchor_w           # 框的宽度
h = (sigmoid(h_raw) * 2)² * anchor_h           # 框的高度
```

这些公式看起来复杂，但核心思路是：**网络输出的是"微调量"，最终坐标 = 网格位置 + 微调量**。

**NMS（非极大值抑制）**：

YOLO 可能对同一辆车产生多个重叠的检测框。NMS 的作用是去重：
1. 按置信度从高到低排序所有框
2. 取出最高分的框，保留
3. 删除所有和它重叠太多（IoU > 阈值）的框
4. 重复 2-3，直到没有剩余的框

```
去重前:  ▯▯▯ (三个重叠框指向同一辆车)
去重后:  ▯   (只保留最高分的那个)
```

### 6.3 颜色投票机制

同一个人从不同角度看，衣服颜色是一样的。但算法不同 — 不同帧可能把同一辆车判为不同颜色。为什么？

- 光照变化（阳光 vs 阴影）
- 检测框包含不同比例的车辆/背景
- 车辆旋转或部分遮挡

**投票机制**解决了这个问题：

```
车辆 #15 在 20 帧中被检测到:
  第5帧:  白色
  第6帧:  白色
  第7帧:  白色
  第8帧:  其他    ← 可能是阴影或遮挡
  第9帧:  白色
  ...

投票结果: "白色" 出现 18 次, "其他" 出现 2 次
最终判定: 白色 ✓（少数服从多数）
```

### 7.2 配置参数


**CONF_THRESH（置信度阈值）的选择**：0.25 是一个折中值。
- 太低（0.1）→ 很多误检（把树影、垃圾桶当成车）
- 太高（0.5）→ 很多漏检（远处的小车检不出来）
- 0.25 配合 ByteTrack 的双阈值机制，低分检测也会参与跟踪，但不创建新轨迹

### 7.3 车辆类别映射

```python
VEHICLE_CLASSES = {
    2: "小汽车",   # COCO 类别 car
    3: "其他",     # COCO 类别 motorcycle → 归为"其他"
    5: "公交车",   # COCO 类别 bus
    7: "卡车",     # COCO 类别 truck
}
```

COCO 80 类中只有这 4 个与车辆相关。其余 76 类（人、狗、椅子...）被过滤掉。

### 7.4 公交车误判纠正

YOLOv8n 在 COCO 数据集上预训练，COCO 的车辆类别粗粒度（仅 car/bus/truck/motorcycle），没有水泥罐车、工程车等特殊车辆类别。这些车辆在特征空间中可能与公交车接近（高大的方形轮廓），导致误判。

针对此问题，系统加入了**双重校验机制**：

**校验 1 — 宽高比（Aspect Ratio）**：

```
公交车:  宽/高 > 2.0（横向长矩形，车身长而矮）
水泥罐车: 宽/高 ≈ 1.0-1.5（更接近正方形）
```

当 YOLO 判定为公交车但 bbox 宽高比 < 1.7 时，几何特征不符，纠正为"其他"。

**校验 2 — 置信度阈值**：

非典型车辆被误判为公交车时，模型置信度通常偏低。当置信度 < 0.5 时，改判为"其他"。

```python
if cls_id == 5:  # bus
    aspect_ratio = w / h
    if conf < 0.5 or aspect_ratio < 1.7:
        cls_id = 3  # 改判为"其他"
```

**类型投票机制**：与颜色识别类似，不再以首次出现的类别为准，而是收集每辆车在所有帧中的类别判定，取多数票作为最终类型。这样即使某几帧误判，最终结果也不会被锁定。

### 7.5 颜色分类函数

```python
def classify_color(roi):
    if roi.size == 0:
        return "其他"

    # 1. BGR → HSV
    hsv = cv2.cvtColor(roi, cv2.COLOR_BGR2HSV)

    # 2. 只取中心 60% 区域（排除边框背景干扰）
    h, w = hsv.shape[:2]
    cy, cx = h // 2, w // 2
    crop = hsv[int(cy - h * 0.3):int(cy + h * 0.3),
               int(cx - w * 0.3):int(cx + w * 0.3)]

    # 3. 创建颜色掩码并计算占比
    total = crop.shape[0] * crop.shape[1]

    white = cv2.inRange(crop, np.array([0, 0, 150]),  np.array([180, 45, 255]))
    black = cv2.inRange(crop, np.array([0, 0, 0]),    np.array([180, 255, 80]))
    red1  = cv2.inRange(crop, np.array([0, 50, 50]),  np.array([10, 255, 255]))
    red2  = cv2.inRange(crop, np.array([170, 50, 50]), np.array([180, 255, 255]))

    w_ratio = np.count_nonzero(white) / total
    b_ratio = np.count_nonzero(black) / total
    r_ratio = (np.count_nonzero(red1) + np.count_nonzero(red2)) / total

    # 4. 按特异度从高到低判断（红色最特异，白色最普遍）
    if r_ratio > 0.25:   return "红色"
    if b_ratio > 0.4:    return "黑色"
    if w_ratio > 0.3:    return "白色"
    return "其他"
```

**为什么按这个顺序判断？** 如果先判断白色，红色车可能在低饱和度区域也被部分判为白色。红色是最特异的颜色（路上最少见），所以优先判断。

**为什么红色需要两个范围？**

在 OpenCV 的 HSV 中，色相 H 的范围是 0-180（不是 0-360），红色位于色环的"两端"：

```
    0°          10°                    170°        180°
    ├────────────┤──────────────────────├────────────┤
    红色          红橙...               ...紫红       红色
```

所以检测红色需要两个区间：`[0, 10]` 和 `[170, 180]`。

### 7.6 中文渲染函数

```python
def draw_chinese_labels(frame, annotations, font_path, info_texts):
    # 1. OpenCV BGR → PIL RGB（颜色空间转换）
    pil_img = Image.fromarray(cv2.cvtColor(frame, cv2.COLOR_BGR2RGB))
    draw = ImageDraw.Draw(pil_img)

    # 2. 用 Pillow 绘制所有中文文本
    for text, pos, color in annotations:
        draw.text(pos, text, font=ft14, fill=color)

    for text, pos, color, size in info_texts:
        draw.text(pos, text, font=ft, fill=color)

    # 3. PIL RGB → OpenCV BGR（转回来）
    result = cv2.cvtColor(np.array(pil_img), cv2.COLOR_RGB2BGR)
    frame[:] = result[:]
```

**为什么这么麻烦？** OpenCV 的 `cv2.putText()` 使用 Hershey 字体，只支持 ASCII 字符（英文、数字）。中文、日文、韩文字符都会变成 `????`。解决方法是借用 Pillow 库，它能加载系统字体（如微软雅黑 .ttc）渲染中文。

**性能优化**：整帧只转换一次（BGR→RGB→PIL→RGB→BGR），所有文本一次性绘制，而不是每行文字转换一次。

### 7.7 主循环

主循环的逻辑可以概括为 5 个步骤：

```
while 视频还有帧:
    1. 读一帧
    2. YOLO + ByteTrack → 检测并跟踪所有车辆
    3. 对每辆车做颜色识别 + 颜色投票
    4. 在帧上绘制中文标注
    5. 写入输出视频
```

**关键代码段**：

```python
# 核心的一行：检测 + 跟踪 一步完成
results = model.track(
    frame,                        # 输入帧
    persist=True,                 # 跨帧保持 track ID
    tracker='bytetrack.yaml',     # 使用 ByteTrack
    conf=CONF_THRESH,             # 置信度阈值
    classes=[2, 5, 7],           # 只检测车辆
    verbose=False                 # 不打印调试信息
)
```

`model.track()` 内部做了以下事情：
1. YOLOv8 检测 → 得到所有车辆的位置框
2. ByteTrack 跟踪 → 给每个框关联一个 track_id
3. 返回带 track_id 的检测结果

### 7.8 结果统计

```python
# 对每辆被跟踪过的车：
for tid in color_votes:
    vtype = id_to_type[tid]                               # 车辆类型
    final_color = Counter(color_votes[tid]).most_common(1)[0][0]  # 颜色投票结果
    type_stats[vtype] += 1
    color_stats[final_color] += 1
```

`Counter.most_common(1)[0][0]` 的含义：
1. `Counter([...])` — 统计每个颜色出现的次数
2. `.most_common(1)` — 返回出现次数最多的 1 个元素 → `[("白色", 18)]`
3. `[0]` — 取第一个元组 → `("白色", 18)`
4. `[0]` — 取颜色名 → `"白色"`

## 8. 常见问题

### Q1: 为什么只数出 12 辆车？（v1 版本的问题）

**A**: 最初的版本使用了一条"虚拟计数线"（画面 60% 高度处），只有车辆中心跨过这条线才计数。大量车辆可能已经在线的一侧出现后不再跨越，导致严重少计。

**修复**: 改用 ByteTrack 跟踪 + 统计所看唯一 ID 的方式。

### Q2: 为什么输出视频上的中文是乱码/问号？

**A**: OpenCV 的 `putText` 不支持中文。v3 版本改用 Pillow + 系统字体（微软雅黑）渲染中文，已修复。

### Q3: 为什么没有用到 NPU？

**A**: Intel Core Ultra 7 155H 确实有 NPU，但 Ultralytics 框架的 ByteTrack 在调用 OpenVINO 时内部指定了 CPU 设备。尝试用底层 OpenVINO API 调用 NPU + 独立的 ByteTrack 实现，但跟踪效果有差距。目前 CPU 模式 36 fps 对于 2660 帧视频来说完全够用。

### Q4: 颜色识别准确吗？

**A**: 有一定的局限性：
- 银色/灰色车辆会被判定为"白色"（低饱和度 + 中等亮度）
- 深蓝/深灰可能被判为"黑色"
- 黄昏/阴天等极端光照下准确率下降
- 颜色投票机制可以在一定程度上纠正单帧误判

### Q5: 能处理其他视频吗？

**A**: 可以。将新视频放入项目目录，修改 `main.py` 中的 `VIDEO_PATH` 变量指向新视频即可。只要视频中有车辆（car/bus/truck），无需重新训练。

## 9. 扩展方向

### 9.1 改用更大模型提高检测精度

将 `export_model.py` 中的 `yolov8n.pt` 改为 `yolov8s.pt` 或 `yolov8m.pt`，检测更准但速度更慢。

### 9.2 添加车牌识别

如果视频分辨率足够高（1080P+），可以在车辆检测框内再加一个车牌检测 + OCR（光学字符识别）模块。当前视频 854×480，车辆太远，车牌不可辨识。

### 9.3 添加速度估计

利用跟踪得到的轨迹 + 帧率信息，可估算每辆车的行驶速度：

```
速度 = 位移（像素） × 像素到实际距离的比例 ÷ 时间（帧数/fps）
```

需要已知场景中的参考距离（如车道线长度）。

### 9.4 实时监控

当前是离线处理视频文件。改为读取摄像头流（`cv2.VideoCapture(0)`）即可实现实时监控。

### 9.5 数据持久化

将统计结果写入数据库（如 SQLite），用于长期趋势分析。
